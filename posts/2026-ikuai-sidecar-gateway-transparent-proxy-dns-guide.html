家庭与工作室网络重构：iKuai 结合分流网关实现透明代理、防 DNS 泄漏与流媒体分流全解

2026-10-16 技术教程 / 网络架构 iKuai · 旁路由 · 透明代理 · Fake-IP · DNS泄漏 · 流媒体分流 · TProxy

在现代高带宽接入（千兆/多千兆光纤）普及的背景下，单一硬件网关往往面临“性能与功能不可兼得”的瓶颈：企业级硬路由（如 iKuai）拥有极致的多拨、流控、DPI 流量识别与硬件 NAT 性能，但缺乏灵活的七层数据重写与规则分流能力；而各类开源软件网关（OpenWrt、基于 Linux 的 Clash/Mihomo/Sing-box 容器或虚拟机）虽分流强大，但其软件软桥接与 PPPoE 性能常成为吞吐瓶颈。

将 iKuai 作为主路由（掌管数据链路与流控），搭配 分流网关（旁路网关，掌管加密隧道、规则分流与 DNS 处理），已成为高级网络玩家和技术工作室的最佳实践。本文将从网络拓扑、数据链路生命周期、DNS 深度防泄漏及生产级配置实战四个维度，对该架构进行系统级全景解构。

一、 架构总览：主旁路由协同与流量闭环拓扑

1.1 职能解耦原则：主路稳健，旁路敏捷

两套系统协同的核心是职责边界严格隔离：

  • 主路由（iKuai）：承担第一层实体物理接入。负责 WAN 口物理多拨/负载均衡、静态与动态 DHCP 地址下发、ARP 绑定、基于 DPI 的协议流控与 QoS 优先级调度。
  • 分流网关（Side Gateway / Transparent Proxy）：承担四至七层流量调度。负责透明代理（TProxy/TUN）、DNS 劫持解析与精准分流、海外加密隧道封装，不运行任何 DHCP 服务，避免局域网内出现不可控的二层广播竞争。

1.2 流量流向闭环：单网卡与双网卡环境解析

模式 A：单臂/单网卡旁路网关

分流网关仅有一根物理/虚拟网线接入内网 LAN。所有经过旁路网关处理的数据，都需要通过该网卡“进”再“出”，吞吐受单网卡双向总线带宽限制。

  • 直连流量：终端 -> 旁路网关 (判定 DIRECT) -> iKuai LAN 口 -> iKuai WAN 口 -> 互联网
  • 代理加密流量：终端 -> 旁路网关 (TProxy 截获 -> 隧道加密封装) -> iKuai WAN 口 -> 海外节点

模式 B：双网卡旁路网关

网卡 1（LAN）面向局域网交换机，网卡 2（WAN）直连 iKuai 的独立子网口，物理上杜绝内网二层环路风险，且吞吐不受单端口全双工拥塞制约。

⚠️ 关键陷阱：非对称路由与 ICMP 重定向引发的链路崩溃
1. ICMP 重定向：当终端配置网关为 192.168.1.254，旁路将直连包转给 192.168.1.1 时，Linux 内核默认会发出 ICMP Redirect 告知终端“下一跳直接找 1.1”，导致分流失效。
2. NAT 回环丢包：若旁路网关转发直连流量时未做 MASQUERADE（SNAT），终端发送目标是 1.254，收到的源 IP 却是 1.1，终端协议栈将判定为非法包直接 RST 拒绝。
根治方案：关闭所有接口的 ICMP 重定向（net.ipv4.conf.all.send_redirects=0），并在旁路网关出口执行 MASQUERADE。

二、 核心实操配置：iKuai 端精准下发与网络隔离

2.1 DHCP Option 3 与 Option 6 黄金组合

在 iKuai 内配置两个独立的 DHCP 作用域或静态 DHCP 分组：

  1. 默认池（IoT/家电/办公设备，保证 99.999% 高可用）：网关（Option 3）与 DNS（Option 6）均直指 iKuai（192.168.1.1）。即使旁路拔线或宕机，全家基础网络不受丝毫影响。
  2. 工作站/加速池（PC、Mac、游戏机、Apple TV）：针对特定 MAC 静态绑定，网关（Option 3）与 DNS（Option 6）统一指向旁路网关（192.168.1.254）。
💡 绝对准则： 指向旁路网关的终端，其 DNS 必须与网关保持一致（同指 192.168.1.254）。若将 DNS 留给 iKuai，终端发起的 DNS 请求将率先在 iKuai 上完成境内明文解析，分流网关收到的将只有解析后的真实 IP，不仅会触发运营商 DNS 劫持，还会使流媒体分流彻底失效。

三、 DNS 架构重构与流媒体分流决策引擎

3.1 解析模式演进对比：Redir-Host vs Fake-IP

评估维度 传统 Redir-Host（真实 IP 模式） 纯 Fake-IP（虚拟 IP 映射模式）
首包解析延迟 较高（必须先向海外上游 DNS 查询完成，约 150-300ms） 接近 0ms（网关即刻返回 198.18.0.0/15 虚拟保留 IP）
DNS 泄漏风险 中高（配置不当极易混杂国内/国外上游） 几乎为零（所有海外域名不产生本地真实解析）
流媒体分流精度 依赖 IP-CIDR 与后置反查，容易出现分流漂移 极高（根据初始 Host/SNI 域名直接精准命中规则）
UDP 游戏与 P2P 兼容性好，天然支持 STUN/Full-cone NAT 需配合 STUN 穿透规则，部分旧协议联机需设排除项

3.2 生产级配置模板（Mihomo/Clash）

# /etc/mihomo/config.yaml
port: 7890
socks-port: 7891
tproxy-port: 7895
mode: rule
ipv6: false

tun:
  enable: true
  stack: system
  dns-hijack:
    - 'any:53'
    - 'tcp://any:53'
  auto-route: true
  auto-detect-interface: true

dns:
  enable: true
  listen: 0.0.0.0:53
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  default-nameserver:
    - 223.5.5.5
    - 119.29.29.29
  nameserver:
    - https://223.5.5.5/dns-query
    - https://1.12.12.12/dns-query
  nameserver-policy:
    'geosite:cn,private':
      - https://223.5.5.5/dns-query
    'geosite:geolocation-!cn':
      - https://1.1.1.1/dns-query
      - https://8.8.8.8/dns-query

四、 旁路透明代理核心层实现：TProxy 与内核栈调优

#!/bin/bash
# 开启内核转发并关闭重定向
sysctl -w net.ipv4.ip_forward=1
sysctl -w net.ipv4.conf.all.send_redirects=0
sysctl -w net.ipv4.conf.default.send_redirects=0
sysctl -w net.ipv4.conf.eth0.send_redirects=0

# 创建策略路由表 100
ip rule add fwmark 1 lookup 100
ip route add local 0.0.0.0/0 dev lo table 100

# iptables TProxy 规则
iptables -t mangle -N PROXY_ROUTE
iptables -t mangle -A PROXY_ROUTE -d 0.0.0.0/8 -j RETURN
iptables -t mangle -A PROXY_ROUTE -d 10.0.0.0/8 -j RETURN
iptables -t mangle -A PROXY_ROUTE -d 127.0.0.0/8 -j RETURN
iptables -t mangle -A PROXY_ROUTE -d 172.16.0.0/12 -j RETURN
iptables -t mangle -A PROXY_ROUTE -d 192.168.0.0/16 -j RETURN

iptables -t mangle -A PROXY_ROUTE -p tcp -j TPROXY --on-port 7895 --tproxy-mark 1
iptables -t mangle -A PROXY_ROUTE -p udp -j TPROXY --on-port 7895 --tproxy-mark 1
iptables -t mangle -A PREROUTING -j PROXY_ROUTE

# TCP MSS Clamping 调优
iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
